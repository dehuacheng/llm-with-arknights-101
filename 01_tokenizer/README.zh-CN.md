# 阶段 01 — 分词器：实验报告

**[English](README.md) | 简体中文**

语言模型在学会任何东西之前，得先会*读*——而对计算机来说，"读"意味着把文本
切成一份固定的"碎片清单"，每个碎片叫一个 **token**。负责切分的那个东西就是
**分词器（tokenizer）**，它必须在模型之前先建好。本阶段做的就是这一步。

本项目的 Track A 从零开始构建语言模型，所以分词器我们也不用现成的。本阶段
用纯 Python 实现了一个字节级 BPE（byte-level BPE）——**不依赖 HuggingFace，
也不使用 `tokenizers` 库**（见 `lib/bpe.py`），在《明日方舟》世界观语料上
训练它，并对词表大小做了一轮扫描实验。

**BPE**（byte-pair encoding，字节对编码）背后只有一个想法：它一开始什么都
不知道。它扫一遍语料，找出挨在一起出现次数最多的那两个相邻碎片，把它们粘成
一个新碎片——这就叫一次**合并（merge）**。然后重复，重复成千上万次。靠前的
合并把字节粘成汉字，靠后的把汉字粘成词。

扫描实验最直接的结果是一个数字——随着词表增大，*fertility* 下降，但收益
递减。不过真正值得一看的，是**合并日志（merge log）**：算法做过的每一次
合并、按顺序排成的完整清单——可以说是它的"日记"。倒回去读这本日记，你能
看着算法一步一粘地自学，学会"罗德岛"是一个词——而"罗德"单独拿出来不是。
本报告依次讲这两部分：那个数字，和那本日记。

---

## 1. 实验设置

**语料。** 阶段 00 产出的 `train` 划分：838 个清洗后的世界观文本文件，共
1166 万字符，绝大部分是中文。`val` / `test` 等留出集在训练中从不出现。

**分词器（`lib/bpe.py`）。**

- **字节级。** 文本即 UTF-8 字节，因此基础字母表就是 256 个字节值——*永远*
  不会有未登录字符（OOV），哪怕是罕见的 CJK 字也一样。一个汉字占 3 个字节；
  BPE 的全部工作就是把这 3 个字节挣回来。
- **从零实现。** 合并训练循环、编码器、解码器、磁盘格式全部手写。训练使用
  增量式的 pair 计数与一个惰性最大堆（lazy max-heap）——正是这个优化让 BPE
  训练变得可行。
- **特殊 token**（保留的 id，永不切分、永不参与合并）：阶段 00 的 28 个结构
  标签（`<正文>`、`<干员名称>` …），外加 `<|bos|>` / `<|eos|>` / `<|pad|>`。
- **预分词（pre-tokenization）** 把文本切成单一字符类的连续段——汉字 / 拉丁
  字母 / 数字 / 空白 / 标点——因此一次合并永远不会跨越类别边界。（这是 GPT-2
  的思路，但换成了更适合中文的规则。）

**扫描实验。** 四种词表大小——4 096 / 8 192 / 16 384 / 32 768——各对应一个
`configs/vocab_*.yaml`。

## 2. 结果 — fertility 随词表大小的变化

**fertility** 是衡量分词器的标准指标：每个字符平均切出多少 token。越低
越好——它意味着同样的文本被压进了更短的序列，模型训练起来就更快、更省。
`tok/Han` 只除以汉字数，`tok/char` 除以全部字符数。

| 词表   | 合并数 | train tok/Han | val tok/Han | test_t1 | test_t2 | 训练耗时 |
|--------|--------|---------------|-------------|---------|---------|----------|
| 4 096  | 3 809  | 0.962         | 1.034       | 1.023   | 1.018   | 255 s    |
| 8 192  | 7 905  | 0.837         | 0.918       | 0.904   | 0.898   | 270 s    |
| 16 384 | 16 097 | 0.754         | 0.831       | 0.819   | 0.815   | 281 s    |
| 32 768 | 32 481 | 0.695         | 0.772       | 0.753   | 0.751   | 290 s    |

一个不做任何合并的纯字节分词器，会在每个汉字上花掉约 3 个 token。即使是 4k
词表，也已经把这个数字压到约 1.0——3 倍的收益——因为常见的整词被并成了单个
token。

四点发现：

- **收益递减。** 词表每翻一倍，买到的收益越来越小：train `tok/Han` 依次下降
  0.125、0.083、0.059。词表扩大 **8 倍（4k → 32k），fertility 只降低约
  28%**，而模型的嵌入表（词表 × d_model）却要大 8 倍。这个取舍是阶段 02 要
  面对的问题。
- **训练集与留出集之间的差距很小、且基本不变。** `val − train` 依次为
  0.072 / 0.081 / 0.077 / 0.077——词表确实在一定程度上贴合了训练集，但更大的
  词表并*不会*把这个差距撑大。
- **时间上更靠后的 test 并不比随机的 val 更难**（就 fertility 而言）。截止
  日期之后的 `test` 划分得分甚至*略好于*随机抽取的 `val` 留出集。fertility
  只是可压缩性，并不是建模难度——截止之后的支线剧情在文风上与训练集主体很
  接近。
- **训练耗时基本恒定（约 255–290 秒）**，与词表大小无关。开销主要在固定工作
  上——读 838 个文件、对 1166 万字符做预分词、建立初始 pair 计数——而不在
  合并循环本身。增量更新的设计让 32k 次合并几乎和 4k 一样便宜。

## 3. 读那本日记 — 追踪《明日方舟》专有名词

每次训练都会把完整的合并日志写到 `data/tokenizers/<name>/merge_log.txt`。
`ByteBPE.trace()`（以及 `trace.py`）则反过来读它：给它一个词，它会把构成
这个词的每一次合并都挑出来，按 BPE 学到的顺序列出——这就是这个词的"一生"，
从原始字节一路长到单个 token。因为 BPE 是贪心的（永远先合并*当前*频次最高的
那一对），一条 trace 就是一次严格自底向上的搭建：又小又常见的碎片在前，又
稀有又完整的整体在最后。下面所有 trace 均取自 32k 分词器。

### 3.1 罗德岛 — 字节 → 字 → 词

```
罗德岛  ->  1 token
  #37    count 96,613   b'\xe5\xbe' = b'\xe5' + b'\xbe'
  #142   count 27,850   '德'        = b'\xe5\xbe' + b'\xb7'
  #169   count 23,247   b'\xe7\xbd' = b'\xe7' + b'\xbd'
  #251   count 16,294   '罗'        = b'\xe7\xbd' + b'\x97'
  #307   count 13,154   b'\xe5\xb2' = b'\xe5' + b'\xb2'
  #383   count  9,741   '岛'        = b'\xe5\xb2' + b'\x9b'
  #391   count  9,567   '罗德'      = '罗' + '德'
  #392   count  9,554   '罗德岛'    = '罗德' + '岛'
```

自底向上三层。先是**字节对**（`#37`、`#169`、`#307`）——每一个都是一族
UTF-8 汉字的共享 2 字节前缀，在任何一个完整汉字出现之前就被合并了。然后是
**汉字**：当第三个字节到位时，字才成形（`#142` 德、`#251` 罗、`#383` 岛）。
最后是**词**：`罗`+`德`→`罗德`，紧接着 `罗德`+`岛`→`罗德岛`。

看最后两行的频次：`罗德` 9,567，`罗德岛` 9,554——只差 13。在这份语料里，
`罗德` 这个片段有 **99.9%** 的情况下就是 `罗德岛`；`罗德` 算不上一个词，它
几乎只作为"罗德岛"的开头存在。

### 3.2 凯尔希 — 后缀先成为 token

```
凯尔希  ->  1 token   （字节对的行已省略）
  #79    count 45,770   '尔'     = b'\xe5\xb0' + b'\x94'
  #192   count 21,059   '希'     = b'\xe5\xb8' + b'\x8c'
  #368   count 10,057   '凯'     = b'\xe5\x87' + b'\xaf'
  #451   count  8,261   '尔希'   = '尔' + '希'
  #454   count  8,139   '凯尔希' = '凯' + '尔希'
```

`尔希` 在 `#451` 就成为独立 token，比完整的名字（`#454`）早了三次合并。`尔`
是整份语料中频次最高的字之一（45,770）——它是音译名字的"黏合剂"（凯**尔**希、
切**尔**诺伯格 …）。BPE 先合并了频次更高的 `尔`+`希`，再把 `凯` 接上去。

### 3.3 前缀本身是不是一个词？看频次。

一个复合词与它的前缀之间的频次差距，能告诉你这个前缀能否独立存在：

```
#391   count 9,567   '罗德'                       罗德岛(9,554) 的前缀 —— 几乎不是词
#532   count 6,759   '源石'                       一个被大量独立使用的词
#1336  count 1,939   '源石技艺' = '源石' + '技艺'   复合词，比它的前缀稀有 3.5 倍
```

`源石`（一种物质）在 `#532` 被合并出来，被使用了 6,759 次；而复合词 `源石技艺`
只有 1,939 次。前缀远多于复合词——`源石` 本身就是一个独立的词。相比之下
`罗德` 几乎不能脱离它的复合词存活。同样形状的 trace，语言学含义却相反——而
正是那一列频次把它们区分开。

### 3.4 长尾 — 罗德岛制药

```
罗德岛制药  ->  1 token   （靠前的行已省略）
  #392    count 9,554   '罗德岛'     = '罗德' + '岛'
  #11255  count    92   '制药'       = '制' + '药'
  #26287  count    27   '罗德岛制药' = '罗德岛' + '制药'
```

完整的公司名"罗德岛制药"复用了 #392 合并出的 `罗德岛` token，但它自己直到
**#26,287** 才被合并，频次只有 27。这正是第 2 节那条收益递减曲线，落在单个
词上的样子：越靠后的合并，每个能省下的 token 越少。

### 3.5 PRTS — 一个英文词，没有字节阶段

```
PRTS  ->  1 token
  #4666  count 354   'RT'   = 'R' + 'T'
  #5473  count 279   'PRT'  = 'P' + 'RT'
  #5488  count 279   'PRTS' = 'PRT' + 'S'
```

ASCII 字母本身就是单字节，所以没有"字节拼装"那一层——trace 直接从字母开始。
`PRT` 和 `PRTS` 的频次完全相同，都是 279：语料里每一个 `PRT` 都是 `PRTS`
（那个世界里的操作系统）的一部分。和 `罗德` 一样，`PRT` 不是词——它只是一个
永远只出现在某个名字里的片段。（像 `Logos`、`Lancet` 这样的干员代号，trace
出来也是同样的形状——用 `trace.py` 跑一下就能看到。）

### 3.6 BPE 学到的不只是词，还有结构

一些被合并得最多的 token 根本不是词，而是文本中反复出现的*形状*：

```
#10   count 237,751   '....'   = '..' + '..'
#27   count 118,362   '......' = '....' + '..'    对话里的省略号，并成一个 token
#551  count   6,494   '\n\n'   = '\n' + '\n'       一个空行 / 段落分隔
#791  count   3,885   '？？？:' = '？？' + '？:'      "未知说话人"的对话标签
```

阶段 00 把说话人标签保留为普通文本（只有*结构*标签才是保留的特殊 token），
所以 BPE 可以自由地发现"神秘说话人"标签 `？？？:` 是一个反复出现的整体——它
确实做到了，在第 791 次合并时把它并成了一个 token。

## 4. 对一整句真实文本分词

一条 trace 追踪的是单个词；这里展示的是一整句真实的世界观文本被分词的样子。
这句文本是阿米娅的游戏内**招募台词**——一句简短、面向公众的台词——分别在最小
和最大的词表下切分：

> 罗德岛公开领导人阿米娅，将与你并肩作战。加油，博士。

```
词表  4 096  — 20 个 token / 26 字符
  罗德岛 | 公 | 开 | 领 | 导 | 人 | 阿米娅 | ， | 将 | 与 | 你 | 并 | 肩 | 作战 | 。 | 加 | 油 | ， | 博士 | 。

词表 32 768  — 13 个 token / 26 字符
  罗德岛 | 公开 | 领导人 | 阿米娅 | ， | 将 | 与你 | 并肩作战 | 。 | 加油 | ， | 博士 | 。
```

两种词表都已经把专有名词 `罗德岛`、`阿米娅`、`博士` 整体保留——它们正是第 3
节里 trace 出来的那些单 token。区别在于*连接性的部分*：在 4k 下，`公开领导人`
是五个松散的字、`并肩` 被切开；在 32k 下它们合成了 `公开` | `领导人`，而
`并肩作战` 成为单个 token。同一句话，20 → 13 个 token——第 2 节那条 fertility
曲线，落在一个句子上的具体样子。

在原文件里，这句台词被结构标签 `<干员招聘文本>` 包裹，而该标签是一个保留的
特殊 token——它作为单个 id 输出，永不参与 BPE 合并（见第 1 节）。

## 5. 自检（sanity checks）

`ByteBPE.sanity_check()` 在每次训练后都会运行（在后续阶段 `ByteBPE.load`
之后也可复用）。四个分词器全部通过五项检查：

- **词表布局** —— 各部分数量对得上；id 连续无空洞。
- **合并只引用已存在的 id** —— 一次合并只能组合已经存在的 token。
- **特殊 token 保持原子性** —— 每个结构标签 / 控制 token 都恰好编码成它那
  一个保留 id，绝不被切开。
- **合并频次单调不增** —— 贪心 BPE 永远取*当前*频次最高的对，因此每次合并的
  频次只能 ≤ 上一次。这是一条真正的不变量（就是第 3 节里那一列向下走的
  `count`）——它同时也检验了 `lib/bpe.py` 里增量式 pair 计数的正确性。
- **往返无损** —— `decode(encode(t)) == t`；字节级 BPE 永不丢信息。

## 6. 复现

| 文件 | 作用 |
|------|------|
| `lib/bpe.py` | `ByteBPE` —— 训练 / 编码 / 解码 / save / load，外加 `merge_log()`、`trace()`、`sanity_check()`。整个分词器。 |
| `train_tokenizer.py` | 训练一个配置；写出分词器 + `merge_log.txt`；运行自检。 |
| `fertility.py` | 为一个已训练分词器生成 fertility 表与示例切分。 |
| `trace.py` | 追踪一个词的合并路径；默认取一组《明日方舟》专有名词。 |
| `configs/vocab_*.yaml` | 每种词表大小一个；克隆使用，不要原地修改。 |
| `docs/RESULTS.md` | 扫描实验的原始数据表。 |

```sh
pip install -r 01_tokenizer/requirements.txt          # 仅依赖 PyYAML

# 训练（--smoke-test = 在少量文件上用极小词表，做一次快速的端到端冒烟测试）
python3 01_tokenizer/train_tokenizer.py --config 01_tokenizer/configs/vocab_16k.yaml
python3 01_tokenizer/train_tokenizer.py --config 01_tokenizer/configs/vocab_4k.yaml --smoke-test

# 为一个已训练分词器打分
python3 01_tokenizer/fertility.py --name vocab_16k

# 追踪任意词的合并路径
python3 01_tokenizer/trace.py --name vocab_32k 罗德岛 整合运动 PRTS
```

已训练的分词器与完整的 `merge_log.txt` 都落在 `data/tokenizers/<name>/`
目录下——它被 git 忽略，因为合并表里含有大量语料的短字节片段。本报告中引用的
合并示例都是字节对和公开的势力 / 干员名称，分享出来不涉及版权问题。

## 7. 给学习者的话 — `EXERCISE` 代码块

这是一个学习项目，本阶段是用来*重新实现*的，不只是读。为了让这一点落到实处，
`lib/bpe.py` 里真正构成算法的那四块代码，都用 `EXERCISE` 标记包了起来：

| 代码块 | 你要实现的部分 |
|--------|----------------|
| `train-merge-loop` | BPE 训练循环 —— 从 pair 计数里学出合并。第 3 节就是它的可视化答案。 |
| `apply-merges` | 把学到的合并重新作用到一个预分词单元上，按 rank 从小到大。 |
| `encode` | 文本 → token id：特殊 token、预分词、BOS/EOS。 |
| `decode` | token id → 文本，在字符边界处缓冲字节。 |

每个代码块长这样——学习者需要的说明就写在开头：

```python
# === EXERCISE START: decode ========================================
# Concept / Given / Produce / Steps  —— 完整说明就写在这里
# --------------------------------------------------------------------
        ...参考实现...
# === EXERCISE END: decode ==========================================
```

学习方法：**删掉两个标记之间的代码**，照着代码块开头的说明自己重写。提交进
仓库的版本*就是*参考答案——`git diff lib/bpe.py` 会告诉你你的版本偏离了多少。
想知道它到底能不能跑通，就重新训练一个极小的分词器，让自检（第 5 节）给你
打分：

```sh
python3 01_tokenizer/train_tokenizer.py --config 01_tokenizer/configs/vocab_4k.yaml --smoke-test
```

`EXERCISE` 块以外的一切——正则预分词器、JSON 的 save/load、`trace()`——都是
给定的脚手架；这四个块才是值得自己动手写的部分。同样的约定会延续到后续
从零实现的（Track A）阶段。
